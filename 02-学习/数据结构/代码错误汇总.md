# 代码错误汇总

> 范围：本轮从 `ArrayList<T>`（顺序表）到队列、双端队列、最小优先级队列的手写实现过程。  
> 目的：记录**实际出现过或在验收中暴露的错误模式**，以后写新的链式/循环/动态数组结构时可直接拿来做检查单。  
> 注：诸如“强异常安全”“随机 STL 差分测试”“移动后对象再次写入”等暂缓的质量提升项，不等同于已经发生的功能错误，故放在文末单列。

---

## 一、最重要的总原则：先写不变量，再写状态转换

这段实现里，大多数问题并非算法不会，而是一次操作只改了局部，没有让整个对象状态保持一致。

每次写完一个会改变结构的函数（插入、删除、扩容、清空、复制、移动），都应问：

```text
1. 指针 / 下标是否仍指向约定的位置？
2. size_ 是否与实际元素数一致？
3. 空结构和单元素结构是否仍满足约定？
4. 头尾、前后、读写位置等成对状态是否同步？
5. 资源所有权是否仍唯一且清楚？
```

可以把它浓缩为一句话：

> **每次状态转移后，不变量必须同时成立；不能只让“当前操作看起来能跑”。**

# 二、线性表与链表

## 1. `erase()`：删完一个节点/元素，不只是在“删除”

### 现象 / 风险

在单链表和双向链表的 `erase()` 路径中，最容易遗漏：

- 删除头结点后，`head_` 已更新，但空表时 `tail_` 没有同步置空；
- 删除尾结点后，`tail_` 已更新，但新尾结点的 `next` 没有置为 `nullptr`；
- 删除唯一元素后，结构表面上少了元素，但 `head_`、`tail_`、`size_` 仍留有旧状态；
- 删除后还能继续 `push_back()`，此时旧的尾指针错误会变成更隐蔽的崩溃或链断裂。

### 根因

把“删掉目标节点”当成了全部工作，忽略了删除操作实际有多个不同状态：

```text
删头 / 删中间 / 删尾 / 删唯一元素
```

其中“唯一元素”同时属于删头和删尾，必须单独验证。

### 正确检查

```text
删除后：
- size_ 减 1；
- 若 size_ == 0：head_ == nullptr && tail_ == nullptr；
- 若非空：head_->prev == nullptr（双链表）；tail_->next == nullptr；
- 删除中间节点时，前后链接均须重新接通。
```

### 固定测试路径

```text
[10, 20, 30]
→ erase(0)        // 删头
→ erase(1)        // 此时删尾
→ erase(0)        // 删唯一元素
→ push_back(42)   // 验证删空后仍能复用
```

## 2. 双向链表：`next` 和 `prev` 必须成对维护

### 容易出现的错误

刚开始写双向链表时，容易把它理解为“单链表多补一条上行链接”。方向对，但若只补其中一边，就会造成双向不一致。例如插入时只做：

```cpp
cur->next = next;
```

却忘了：

```cpp
next->prev = cur;
```

或者删除一个中间节点时，只让前驱跳过它，却没有让后继回指前驱。

### 核心不变量

对任意相邻节点 `p`、`q`：

```text
p->next == q  <=>  q->prev == p
```

边界还应满足：

```text
head_->prev == nullptr
tail_->next == nullptr
```

### 实用写法

插入一个位于 `left` 与 `right` 之间的新节点 `node` 时，按“四条边”逐项写：

```cpp
node->prev = left;
node->next = right;
if (left != nullptr) left->next = node;
if (right != nullptr) right->prev = node;
```

不要只凭感觉补链接；把四个方向都列出来，更不容易漏。

---

## 3. 泛型容器不要偷偷要求 `T` 能默认构造

### 出现的问题

线性表的 `erase()` 曾有“返回值先默认构造、之后再赋值”的实现倾向。这会无意中要求：

```cpp
T value;  // 要求 T 可默认构造
```

而接口本身并没有这项约束。于是像只有带参构造函数的类型，会在编译期失败。

### 教训

模板容器应只施加接口真正需要的约束。`erase()` 的返回值应直接由被删元素初始化，而不是先造一个无意义的默认对象。

### 自检问题

> 若把 `int` 替换成一个“不可默认构造，但可拷贝/移动”的类型，这个容器是否仍能编译？

# 三、循环数组：队列与双端队列

## 4. 无符号下标不能直接向前减一

### 实际错误模式

`front_`、`rear_` 通常是 `std::size_t`。若写：

```cpp
front_ = (front_ - 1) % capacity_;
rear_ = (rear_ - 1) % capacity_;
```

在下标为 `0` 时会发生无符号下溢：先变成一个极大的整数，再取模。即使某次结果看起来碰巧正确，也不能依赖这种写法。

### 正确写法

```cpp
front_ = (front_ + capacity_ - 1) % capacity_;
rear_ = (rear_ + capacity_ - 1) % capacity_;
```

### 应用位置

- `CircularDeque::push_front()`：队头前移；
- `CircularDeque::pop_back()`：队尾先退一格；
- 任何环形缓冲区的“向左/向前”操作。

### 一句记忆

> 环形数组后退一格：**先补一圈，再减一格。**

---

## 5. `rear_` 的语义没有统一，会导致“取错元素”

### 约定

本项目循环队列/双端队列采用：

```text
front_：当前队头元素的位置
rear_ ：下一个可写位置（不是当前队尾元素的位置）
```

### 易错点

因此 `pop_back()` 不能直接读取 `data_[rear_]`，而应：

```text
rear_ 先退一格
→ 新 rear_ 才是原队尾元素的位置
→ 读取 / 返回 data_[rear_]
```

### 自检图

```text
元素：    [ A ][ B ][ C ][ 空 ]
下标：      0    1    2    3
front_ = 0
rear_  = 3      // 指向下一个可写位置

pop_back() 后：rear_ 应先变为 2，再取 C。
```

---

## 6. 空/满状态必须由统一规则区分

### 本项目策略

循环队列与双端循环队列使用“**始终空出一个位置**”的方案：

```text
empty(): front_ == rear_
full() : (rear_ + 1) % capacity_ == front_
```

这意味着可存元素数为 `capacity_ - 1`。

### 常见误区

- 以为数组长度 `capacity_` 就能装 `capacity_` 个元素；
- 把 `rear_` 当作最后一个元素位置，而又按“下一可写位置”的满队公式判断；
- 只测顺序入队出队，不测绕回，导致“假溢出”或覆盖未出队元素。

### 必测状态路径

```text
入队至接近满
→ 出队若干
→ 再入队，使 rear_ 绕回数组开头
→ 检查 FIFO 顺序、满队异常与可用空间是否正确
```

---

## 7. `clear()` 写成比较而非赋值：代码能编译，却什么也没做

### 实际错误

曾出现过类似：

```cpp
front_ == rear_;
```

这只是布尔比较表达式，对状态没有任何改变。

### 正确思路

`clear()` 不是“检查是否为空”，而是“把对象恢复为空状态”。例如：

```cpp
front_ = rear_;
```

或将两者一起重置到约定的初始位置，并同步必要的 `size_`。

### 防范方法

对所有副作用函数问一句：

> 这一行是在**计算条件**，还是在**改变状态**？

若编译器开启了足够警告，这类无副作用比较表达式也更容易被发现。

# 四、链式队列：最容易出错的是“空 ↔ 非空”转换

## 8. 首次入队时解引用空 `rear_`

### 实际错误链

空队列中：

```text
front_ == nullptr
rear_  == nullptr
```

若第一次 `enqueue()` 直接写：

```cpp
rear_->next = new_node;
```

会解引用 `nullptr`；同时 `front_` 也没有指向新节点。

### 正确分支

```text
若队列为空：front_ = rear_ = new_node
否则：rear_->next = new_node; rear_ = new_node
```

### 应记住的状态转移

```text
空队列 --enqueue--> 单节点队列
```

这是最特殊的一次入队，不可与普通入队混为一谈。

---

## 9. 删除最后一个元素后未清空 `rear_`：悬空指针

### 实际错误链

`dequeue()` 删除队头后，若原来只有一个节点：

```text
front_ 会变成 nullptr
rear_ 仍指向已经 delete 的旧节点
```

后续 `enqueue()` 或析构都可能访问悬空指针。

### 正确处理

```text
删除队头后：
若 front_ == nullptr：rear_ 也必须置为 nullptr
```

### 一句记忆

> 链式队列的 `front_` 与 `rear_` 在“第一个入队”和“最后一个出队”这两个瞬间，必须一起更新。

---

## 10. 只修了指针，漏了 `size_`

### 实际错误

修复空队列首次入队时，若漏写 `size_++`，会产生一种很迷惑的状态：节点实际存在，但：

```text
size_ == 0
empty() == true
front() 却按空队列逻辑抛异常
```

### 经验

指针结构中，`size_` 不是“附属统计”，而是状态的一部分。每个插入/删除操作要同时审查：

```text
链接 / 头尾指针 / size_
```

# 五、接口、命名与编译：小笔误也可能遮住真实逻辑

## 11. 类名、文件名、父类名复制错位

### 实际出现的类型

双端循环队列的初版中曾出现：

- 文件名 `circular_dueqe.hpp` 拼写倒置；
- 继承名写成不存在的 `Dueue<T>`；
- `CircularDeque` 的构造、析构、赋值运算符误写成 `Deque`；
- 头文件包含了 `queue.hpp`，实际应包含 `deque.hpp`。

结果是在业务逻辑尚未运行前就因模板/类名错误无法编译。

### 根因

从已有文件复制骨架后，没有完成“系统性改名”，导致父类与当前类的职责混淆。

### 改进流程

复制一个相近实现后，先做一次纯机械核查：

```text
[ ] 文件名、include guard / #pragma once
[ ] #include 的父接口
[ ] class 当前类名
[ ] 构造 / 析构函数名
[ ] 拷贝构造与移动构造参数类型
[ ] copy/move assignment 的返回类型与参数类型
[ ] CMake target 与测试文件名
```

随后先做最小编译，再写大量测试：

```bash
g++ -std=c++20 -Wall -Wextra -Wpedantic -I. -x c++ -c ds/目标头文件.hpp
```

## 12. 新容器没有注册进 CMake / CTest，就等于没有进入自动回归

### 现象

刚完成 `CircularDeque` 骨架时，工作区没有对应的：

```text
tests/test_circular_deque.cpp
CMakeLists.txt 中 test_circular_deque 目标与 add_test(...)
```

此时即便原有 CTest 全绿，也不能说明新容器正确——它根本没有被编译和执行。

### 教训

“测试通过”必须先确认测试真的覆盖了新增代码。

### 最小闭环

```text
新增实现
→ 新增测试文件
→ CMake 添加可执行目标
→ CTest 注册测试
→ 单独运行新测试
→ 全量 CTest
```

# 六、资源管理与泛型容器的长期检查项

以下并非已经导致功能失败的错误，但在后续 STL 对照与统一收束时必须回头处理。

## 13. 复制赋值的强异常安全

若复制过程中分配/拷贝元素抛异常，原对象是否仍保持原值？

较稳妥的方向是：先创建完整临时副本，成功后再交换（copy-and-swap）。这样失败时不会留下“半复制”的对象状态。

## 14. 移动后对象的可用性约定

移动后的对象必须可析构，通常也应保持可查询、可重新赋值；但是否保证可立刻再次 `enqueue()`，需要在接口契约、实现和测试中统一，而不能靠碰巧。

## 15. 用 STL 做随机差分测试

确定性样例能覆盖典型边界，随机差分测试则更擅长找状态机错误：

```text
ArrayList     ↔ std::vector
链表           ↔ std::list / std::forward_list（按可比接口）
栈             ↔ std::vector 模拟栈
队列 / 双端队列 ↔ std::deque
```

每执行一步随机操作，就比较：元素序列、`size()`、`empty()`、首尾元素及异常行为。它尤其适合捕获循环绕回、删空后复用、复制/移动后的边界问题。

# 七、提交前的个人检查清单

```text
## 状态不变量
[ ] 空结构的所有指针/下标/计数器是否一致？
[ ] 单元素结构是否与一般情况不同？是否单测？
[ ] 头尾（或前后）状态是否同步？
[ ] size_ 是否在每条插入/删除路径中更新一次且仅一次？

## 链式结构
[ ] 头删、尾删、删唯一元素、删空后复用都测过？
[ ] 双链表每条 next 是否有对应 prev？
[ ] 删除后是否留下悬空的 head_ / tail_ / rear_？

## 循环数组
[ ] front_ / rear_ 的语义是否明确且贯彻一致？
[ ] 是否测试绕回？

## 工程闭环
[ ] 类名、构造函数名、文件名、include 是否统一？

```

## 最后的复盘

这一轮最有价值的收获，不是“以后不再写错”，而是逐渐形成一套发现错误的方式：

```text
看不变量
→ 列状态转移
→ 专打边界：空、单元素、满、绕回、删空后复用
→ 让自动测试真正编译并跑到新代码
```

容器代码本来就由大量边界拼成。能反复把这些边界找出来、修到测试全绿，正是在把“会写”变成“写得可靠”。
